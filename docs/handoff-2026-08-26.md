## 2. What was built this session

### The public landing page (`/`)

Ported from an HTML draft Felipe built in another Claude session. The
architectural point that made it safe: **the site is also the app**. Route
groups already separated them —

- `app/(public)/` — what a stranger sees. The landing, public profiles.
- `app/(app)/` — the authenticated screens, **and what the Android WebView
  loads**. Events, cards, sessions, profile.

So the public half can be rewritten without the capture app noticing. If a
future session is asked to "make the site just a marketing page", this is the
distinction to hold: `(app)` cannot be removed without breaking the Android app.

**The wordmark was verified byte for byte** against
`frontend/components/brand/Wordmark.tsx` before anything was ported. The brand
manual forbids a redrawn or regenerated wordmark and it is the easiest rule in
this project to break by accident. Do this check on any imported design.

New components live in `frontend/components/marketing/` — landing only, never
used inside the app.

### The waitlist

- `waitlist_entries`: email (unique), `first_name`, `last_name`, `source`,
  `created_at`. **Nothing else, on purpose.** The page promises "a gente só usa
  seu e-mail pra te avisar dos próximos eventos", and a column we do not have
  is a promise we cannot break by accident later. Resist adding phone,
  birthday, device.
- `POST /api/waitlist` — public, because no account exists at the point someone
  asks. A repeat submission returns 201 with `already_joined: true` and **fills
  in a name we are missing** without overwriting one we hold.
- `GET /api/waitlist/count` — public, a number only.
- `GET /api/waitlist` — gated on `waitlist_admin_emails`, **not** on merely
  being signed in. These are other people's contact details given for one
  stated purpose; every account on the platform is not a reasonable audience.
  Empty by default, so the list is closed until deliberately opened.
- `/admin/waitlist` — the page that makes it readable, with CSV export.
  **Deliberately not in the navigation**: access is decided server-side and the
  frontend cannot know the answer in advance, so a nav link would fail for
  almost everyone who saw it. Reached by URL.

`normalize_email` (lowercase + trim) and `normalize_name` (trim + collapse
whitespace, **nothing else**) live in `backend/app/services/waitlist.py` with
tests. Capitalisation is deliberately not corrected: "de Souza", "McDonald" and
"van der Berg" are spelled the way their owners spell them, and title-casing
would quietly rename people.

### Password recovery

Resend on `mail.tumtum.cc` — a **subdomain**, deliberately. `oi@tumtum.cc`
already receives, so there are live MX records on the root domain; pointing a
sending provider at the root risks replacing them and killing an address nobody
would think to re-test.

Decisions that matter more than the code:

- **The reply never says whether the account exists.** Both outcomes return the
  same sentence. Saying "esse e-mail não está cadastrado" would make the form a
  free tool for discovering who has an account, at any volume, for anyone.
- **The table stores a hash, never the token.** Reading `password_reset_tokens`
  grants nobody a reset. SHA-256 rather than bcrypt is right *here* and wrong
  for a password: 32 random bytes with a 30-minute life have no dictionary to
  run against them.
- **Thirty minutes, one use.** Completing a reset also kills every other
  outstanding link for that account — someone resetting because they fear a
  break-in should not leave a spare key in a mailbox they no longer control.
- **A failed send is logged loudly.** Since the person is told the same thing
  either way, a failure would otherwise vanish and "não recebi o e-mail" would
  be unanswerable. `EmailNotConfigured` raises rather than returning quietly.
- **Replies reach a person.** `mail.tumtum.cc` only sends; `reply_to` points at
  `oi@tumtum.cc`, which receives.
- **The lookup is case-insensitive** (`func.lower`), working around the
  unnormalised `users.email` column — see §5.

Files: `backend/app/services/password_reset.py`, `backend/app/services/email.py`,
`backend/app/models/password_reset_token.py`, endpoints in
`backend/app/api/auth.py`, pages at `/esqueci-senha` and `/redefinir-senha`.

### Signup and login

Reveal toggle (`components/ui/PasswordInput.tsx`, using a new optional
`trailing` slot on `Input`) and a confirmation field on signup. The toggle is
`type="button"` because a bare `<button>` inside a form submits it.

These were built **before** password recovery existed, when a typo meant a
permanently unreachable account. They still matter: the confirmation is what
stops a reset from replacing a password you cannot remember with one you never
saw.

### The browser capture path was retired

"Ao vivo" is out of the navigation. The argument is not preference: **a Polar
H10 accepts two simultaneous BLE connections**, and during an event both are
taken by the app and by Polar's own app recording the reference. A browser
would be the third and would not connect. The menu item offered a route that
could only fail, under the most confident label in the bar.

The `/live` route itself was **kept** — deleting a working screen days before
the only six-hour test buys nothing. `ExperienceActivity` still intercepts it
inside the WebView and drops back to the native capture screen. Revisit after
the festival.

*(The two-connection limit is the H10's documented behaviour and matches what
Felipe hit in practice. It has not been measured by us.)*

## 3. Bugs found and fixed, and the class they belong to

This project has a named recurring bug class, now found **thirteen times**:
**the app stating something false about its own state.** Every one was found by
a person using the thing; none by a test.

This session found the worst ones yet, and they generalise the rule:

### An empty state is a claim

`/events` and `/cards` had **no error handling at all on load**. `loadEvents`
used `try/finally` with no `catch`, so a refused request left the list empty —
and an empty list renders as "Nenhum evento encontrado".

Measured by building both versions and forcing every `/api/**` call to 401:

| under a 401 | before | after |
|---|---|---|
| `/events` | "Nenhum evento encontrado" **+ an offer to seed demo events** | sign-in prompt, working button |
| `/cards` | "Você ainda não criou nenhum card" | sign-in prompt, working button |
| `/sessions`, `/admin/waitlist`, `/events/[id]/editar` | red box, no way out | sign-in prompt, working button |

**The demo-seeding offer is what made this dangerous.** The festival failure
mode was sitting in plain sight: the token expires mid-event, Felipe opens
Eventos, and the app says his event does not exist while inviting him to seed
demo data over the real one.

The rule now in `CLAUDE.md`: **an empty state is a claim about the world.** Any
list that can fail to load must distinguish "nothing there" from "I could not
ask". **An audit of the remaining empty states is queued** — two were found by
pulling one thread and nobody has checked the rest.

### A plausible wrong answer costs more than an error

Opening `/esqueci-senha` before it shipped produced "Perfil não encontrado —
Este usuário não existe", because the `[username]` route caught the path. The
underlying defect was `catch { setError(true) }` catching everything, so an
unreachable server and a genuine 404 rendered the same sentence.

Three outcomes now, in three sets of words, plus the app's **first
`not-found.tsx`** — unknown multi-segment paths were falling through to Next's
default page, unbranded and in English.

### The others

- **`SignInRequired` says less than what it replaced.** A 401 means no valid
  token, which is as often "this browser never signed in" as "your session
  expired". Asserting expiry when someone opened the app on a laptop is the
  same defect one level down.
- **The waitlist form had no handler at all.** Someone typed an address,
  clicked, and nothing happened — no request, no error, no confirmation. The
  lead was lost *and* the person believed they had signed up.
- **The sessions empty state** told people to go to "Ao vivo" after that item
  was removed. Remove the destination, leave the sign, and the app lies again.

## 4. Working rules this session confirmed or earned

### Push everything first, open the PR last

**This failed twice more this session** (#37 and #40 were merged while later
commits were still coming), bringing the count to six. The fourth occurrence
proved the rule was not the fix — it had been written in `CLAUDE.md` since the
third and failed anyway.

What actually removes it, and it is mechanical:

- **Do not open the PR until the work is finished and pushed.** Not "mostly
  finished" — finished.
- If a PR is already open and more commits are coming, **say so in the
  description** so it does not get merged early.
- **Anything pushed after a merge gets a NEW PR.** Never an edit to a merged
  one. When a merged PR's description overstates what it contains, **correct
  the description** with the correction stated at the top, then open the new PR.

PRs from this session: #37, #38, #39, #40, #41, #42 — all merged.

### Establish which build is installed before reading the source

An hour was lost to a launcher icon that "still" showed the Android robot after
the fix had merged. The installed APK was `tumtum-captura-4a12146.apk`, built
before the icon existed. **The APK filename carries the commit — read it
first.**

### Verify in a browser, not by reasoning

Several findings this session only appeared because the *before* state was
actually rendered rather than reasoned about — the demo-seeding offer most of
all. Playwright is available (`/opt/pw-browsers/chromium`); `npx next start` on
a spare port plus a short script is enough.

### Run what CI runs

`Backend Lint` turned red on a formatting-only issue because only
`ruff check app/` was run locally. **CI runs both `ruff check app/` and
`ruff format --check app/`**, with `ruff==0.15.8` pinned — a different local
version can disagree.
