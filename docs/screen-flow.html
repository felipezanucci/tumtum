Visão geral

Este documento registra o fluxo de navegação atualmente implementado no app Tumtum, com base no código-fonte do diretório frontend/app/. O objetivo é servir como referência visual para revisão de produto, identificação de lacunas e alinhamento de prioridades para os próximos sprints.

O que este documento cobre

  • Todas as rotas construídas (públicas, autenticação e app)
  • Gatilhos de navegação entre telas (cliques, redirects, submits)
  • Elementos-chave de cada tela
  • Endpoints de API consumidos
  • Lacunas entre a especificação (CLAUDE.md) e o que está em código

O que este documento NÃO cobre

  • Especificações visuais finais (design system)
  • Estados de loading / erro / vazio de cada componente
  • Integrações externas (HealthKit, Setlist.fm) — ainda não conectadas à UI
  • Geração de card (endpoint existe, UI ainda não dispara)

Observações críticas

  • Sem middleware de auth: as rotas do grupo (app) não têm proteção server-side; o acesso depende das chamadas de API falharem sem JWT válido.
  • Sem gatilho para criar sessão de HR: o fluxo para do detalhe do evento à tela de experiência. A aquisição de dados de batimentos (HealthKit / Health Connect) ainda não está conectada à UI.
  • Sem UI para gerar card: a galeria existe e lista cards, mas não há botão que dispare POST /api/cards a partir de um pico.

Lacunas & próximos passos

Lacunas funcionais priorizadas

P0Aquisição de dados de HR

Sem um caminho para o usuário gerar uma sessão de HR, toda a jornada pós-evento fica inacessível. Hoje a tela de experiência é órfã de entrada.

Impacto
Bloqueia a validação da hipótese central do MVP (ver sua reação emocional ao evento).
Proposta
Construir botão "Registrar sessão" no detalhe do evento que dispare fluxo de sync (HealthKit on-device / Health Connect OAuth) e, ao concluir, redirecione para /experience?session=….
Dependências
Integrações em lib/health/ precisam ser conectadas à UI; endpoint POST /api/health/sync já existe no backend.
P0Geração de card a partir de um pico

A galeria lista cards, mas não há ação que crie um novo. O motor viral do produto está desligado.

Impacto
Impede o momento-chave de compartilhamento, principal canal de crescimento orgânico previsto.
Proposta
Na tela de experiência, clicar em um PeakMarker abre modal de preview do card e dispara POST /api/cards; ao concluir redireciona para /cards destacando o novo item.
Dependências
Serviço card_generator.py e endpoint já existentes no backend.
P1Proteção das rotas autenticadas

Não há middleware.ts; páginas do grupo (app) carregam para qualquer visitante e quebram ao fazer a primeira chamada de API.

Impacto
UX degradada (flash de tela vazia + erro) e superfície de risco para vazamento de dados via componentes client-side.
Proposta
Adicionar middleware.ts que valida cookie/token e redireciona para /login quando ausente nas rotas do grupo (app).
P2Perfil público por username

Rota /[username] existe mas o backend só expõe busca por UUID; o link de share vai gerar 404 na vida real.

Proposta
Adicionar campo username único em users, endpoint GET /api/users/by-username/{username} e atualizar a página para buscar por username.

Telas previstas no CLAUDE.md ainda não implementadas

  • Tela de geração/preview de card — motor viral.
  • Tela de sync / importação de HR — callback do wearable.
  • Esqueci minha senha — fluxo comum de recuperação, ausente no código.
  • Login social (Apple / Google) — previsto, ainda só email/senha.
  • Modo de comparação com artista/atleta — só o card solo existe.
  • Coleções / favoritos — mencionado no produto, sem rota.

Infraestrutura & qualidade

  • Sem Sentry configurado (monitoramento de erros).
  • Sem PostHog (analytics de funil).
  • Sem manifesto PWA / instalabilidade.
  • Sem tasks Celery em uso real (geração de card ainda síncrona).
  • Sem integração ativa com Setlist.fm ou APIs de esportes (eventos são seed manual).

Recomendação para a próxima sprint

Foco sugerido (Sprint 3): fechar a jornada ponta-a-ponta para um único caso (show com Apple HealthKit). Isso significa 4 entregas conectadas: (1) botão de registro na tela do evento, (2) fluxo de sync real em on-device, (3) redirecionamento automático para a tela de experiência após o sync, (4) geração de card a partir de um pico. Tudo o mais (comparação, esportes, Android) fica como P2 até termos o primeiro loop completo validado com usuários.
